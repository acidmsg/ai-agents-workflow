# Правила именования

Применяются ко **всем** текущим и будущим задачам в проекте. Дополняют философию именования из
[`standards.md`](.roo/rules/standards.md) (секция «Ⅳ Стиль — имена говорят сами за себя») конкретными соглашениями.

---

## Общие принципы

- **Язык:** идентификаторы кода, имена файлов, ключи инфраструктуры — строго на английском. Комментарии, контекст логов, документация — на русском (детали в [`core.md`](.roo/rules/core.md)).
- **Длина и ясность:** имя должно описывать «чем является сущность». Максимум 3–4 слова на идентификатор. Краткость предпочтительнее, но не в ущерб понятности.
- **Иерархия:** порядок от общего к частному (например, `user_active`, `user_deleted`, а НЕ `active_user`).

## Файловая система

### Директории и не-кодовые файлы

- Строгий **kebab-case**: `tg-bot-notifier`, `readme.md`, `docker-compose.yml`.
- Без пробелов, без CamelCase, без underscore в именах директорий.

#### Исключения: well-known files корневого уровня

Следующие имена файлов являются устоявшимися стандартами экосистемы Git/GitHub и
**освобождаются** от требования kebab-case:

- `README.md` — стандарт GitHub/GitLab для описания проекта.
- `WIKI.md` — пользовательская документация (аналог `README.md`).
- `LICENSE.md` — текст лицензии.
- `CHANGELOG.md` — история изменений.
- `ARCHITECTURE.md` — архитектурная документация проекта.
- `CONTRIBUTING.md` — руководство для контрибьюторов.
- `SECURITY.md` — политика безопасности.
- `CODE_OF_CONDUCT.md` — кодекс поведения.

Эти файлы пишутся в UPPERCASE (`.md` — строчными) согласно индустриальной конвенции.

### Файлы исходного кода (Python)

- Строгий **snake_case**: `main.py`, `data_parser.py`, `healthcheck.py`.

### Тестовые файлы

- Имя тестового файла должно соответствовать имени тестируемого модуля с префиксом `test_`.
- Пример: модуль `data_parser.py` → тесты `test_data_parser.py`.
- Тесты размещаются в директории, зеркалирующей структуру `src/`: модуль
  `src/handlers/common.py` → тесты `tests/handlers/test_common.py`.
- При наличии нескольких тестовых файлов на один модуль (разные аспекты) —
  объединить в один файл, разделяя логику через классы (`Test*`).
- Конфликт имён (одинаковые имена модулей в разных пакетах) разрешается через
  директорию: `tests/handlers/test_common.py` и `tests/utils/test_common.py` —
  допустимо, т.к. pytest различает их по полному пути.

## Python-код

Базовые правила (`snake_case` для функций/переменных, `PascalCase` для классов) зафиксированы в
[`standards.md`](.roo/rules/standards.md) (PEP-8). Ниже — уточнения и дополнения.

### Классы и типы

- **PascalCase**: `AppointmentParser`, `TUserId`, `ClinicRepository`.

### Функции и методы

- **snake_case**. Обязательно начинаются с глагола: `fetch_data()`, `parse_schedule()`, `get_user()`.
- Исключения:
    - **Свойства** (`@property`) — существительные: `user.is_active`, `config.timeout`.
    - **Callback-обработчики** (aiogram, FastAPI) — глагол подразумевается контекстом:
      `cmd_start()`, `process_fio()`.
    - **Стандартные имена языка/фреймворка:** `main()` (Python entry point),
      `lifespan()` (FastAPI `@asynccontextmanager`).
    - **Фоновые asyncio-циклы:** суффикс `_loop` семантически эквивалентен глаголу
      («выполнять цикл»): `monitor_loop()`, `discovery_loop()`, `cleanup_loop()`.
    - **Паттерн `safe_*`** для атомарных/потокобезопасных операций: `safe_increment()`,
      `safe_set()`. Префикс `safe_` означает «безопасно выполнить операцию».
    - **Трансформеры-утилиты** (аналоги `str()`, `int()`, `repr()`): `safe_name()` —
      функция-преобразователь, возвращающая безопасное строковое представление.

### Переменные

- **snake_case**. Существительные или свойства: `user_id`, `is_active`, `doctor_list`.

### Константы и переменные окружения

- **UPPER_SNAKE_CASE**: `MAX_TIMEOUT = 30`, `API_BASE_URL`, `DEFAULT_RETRY_COUNT`.
- Имена переменных окружения в `.env` также следуют `UPPER_SNAKE_CASE`.

### Приватные члены

- Префикс с одним подчёркиванием: `_handle_internal_error`, `_cache_key`.
- Двойное подчёркивание (name mangling) — только когда действительно нужно избежать конфликта имён в иерархии наследования.

## Инфраструктура

### Конфигурационные ключи (JSON/YAML)

- Строгий **snake_case**: `api_token`, `retry_timeout`, `redis_host`.
- Логическая группировка в пространства имён через точку: `bot.api_token`, `redis.host`, `monitor.interval_sec`.

### База данных

- **Таблицы:** множественное число, **snake_case** (`users`, `appointments`, `clinic_doctors`).
    - Исключение — **неисчисляемые существительные** (mass nouns): `monitoring`, `config` —
      для них множественное число грамматически некорректно.
    - Исключение — **служебные таблицы** с единственной строкой: `schema_version`.
    - **Join-таблицы** (many-to-many): допустим singular для обеих частей
      (`user_monitoring`).
- **Столбцы:** единственное число, **snake_case** (`id`, `created_at`, `user_id`, `is_active`).

## Git-коммиты (Conventional Commits)

Строго формат нижнего регистра: `<type>: <description>`

### Типы коммитов

| Тип        | Назначение                                            |
| ---------- | ----------------------------------------------------- |
| `feat`     | Новая функциональность                                |
| `fix`      | Исправление ошибки                                    |
| `docs`     | Документация (README, WIKI, specs, комментарии)       |
| `refactor` | Реструктуризация кода без изменения поведения         |
| `chore`    | Зависимости, конфигурация, сборка, технические задачи |
| `test`     | Добавление или изменение тестов                       |

### Примеры

- `feat: add doctor discovery service`
- `fix: handle redis timeout in monitor`
- `docs: update architecture diagram`
- `refactor: extract booking validator`
- `chore: bump aiogram to 3.x`
- `test: add integration tests for zdrav client`

### Требования к описанию

- На английском языке.
- Нижний регистр, без завершающей точки.
- Длина первой строки — не более 72 символов.
- При необходимости — тело коммита через пустую строку после заголовка.
